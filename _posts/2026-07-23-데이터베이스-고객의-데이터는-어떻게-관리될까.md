백엔드가 주방이라면, 데이터베이스는 식재료 창고다. 아무리 요리를 잘 해도 재료를 제대로 보관하지 않으면 상한 걸 쓰거나, 어디에 뭘 뒀는지 몰라 헤매게 된다.

---

## 왜 데이터베이스가 필요한가

"그냥 파일에 저장하면 안 되나?"라는 질문에서 시작한다. 사용자가 한 명이면 텍스트 파일이라도 상관없다. 하지만 동시에 여러 사람이 같은 데이터를 읽고 쓰는 순간 문제가 생긴다.

엑셀 파일을 공유 드라이브에 두고 여러 명이 동시에 편집하면 어떻게 되는지 생각하면 된다 — 누군가의 수정이 덮어씌워지거나, 파일이 깨진다. 데이터베이스는 이런 충돌을 방지하면서, 원하는 데이터를 빠르게 찾을 수 있도록 설계된 전문 시스템이다.

## SQL vs NoSQL — 두 가지 철학

데이터베이스는 크게 두 계열로 나뉜다.

### SQL (관계형)

엑셀 시트를 떠올리면 된다. **행(row)**과 **열(column)**이 있는 표 형태로 데이터를 저장한다.

| id | 이름 | 이메일 | 가입일 |
|----|------|--------|--------|
| 1 | 김민수 | min@mail.com | 2026-01-15 |
| 2 | 이지연 | ji@mail.com | 2026-03-22 |

핵심 특징은 **구조가 미리 정해진다**는 점이다. 어떤 열이 있고, 각 열에 어떤 타입의 데이터가 들어가는지를 먼저 정의해야 한다. 디자인 가이드라인처럼 "이 안에서는 이 규칙을 따른다"는 약속이 있는 것.

대표적인 SQL 데이터베이스: PostgreSQL, MySQL, SQLite

### NoSQL (비관계형)

JSON 문서를 서랍에 넣는다고 생각하면 된다. 구조가 유연해서, 문서마다 담긴 항목이 달라도 된다.

```json
{
  "이름": "김민수",
  "이메일": "min@mail.com",
  "취미": ["등산", "요리"]
}
```

다른 문서에는 `취미` 항목이 없어도 괜찮다. 빠르게 구조를 바꿔가며 프로토타이핑하기 좋지만, 데이터 간의 관계가 복잡해지면 관리가 어려워진다.

대표적인 NoSQL 데이터베이스: MongoDB, Firebase

### 어떤 걸 골라야 하나

| 기준 | SQL | NoSQL |
|------|-----|-------|
| 구조 | 엄격 (스키마 고정) | 유연 (스키마 자유) |
| 관계 표현 | 강점 (테이블 간 연결) | 약점 |
| 빠른 프로토타이핑 | 상대적으로 느림 | 빠름 |
| 데이터 무결성 | 강력 | 개발자 책임 |
| AI 학습 데이터 | 풍부 | 상대적으로 적음 |

바이브 코딩에서는 **SQL 계열을 먼저 익히는 게 유리**하다. AI에게 DB 관련 코드를 시킬 때 SQL 기반의 예제가 훨씬 많고, 데이터의 관계를 명확히 정의하는 습관이 나중에 도움이 된다.

## SQL 기본 — 다섯 가지 문장

SQL의 기본 조작은 다섯 문장이면 된다.

```sql
-- 테이블 만들기
CREATE TABLE menus (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  price INTEGER
);

-- 데이터 넣기
INSERT INTO menus (name, price) VALUES ('아메리카노', 4500);

-- 데이터 조회
SELECT name, price FROM menus WHERE price < 5000;

-- 데이터 수정
UPDATE menus SET price = 5000 WHERE name = '아메리카노';

-- 데이터 삭제
DELETE FROM menus WHERE name = '아메리카노';
```

앞 챕터의 CRUD(Create, Read, Update, Delete)와 정확히 대응된다. INSERT = Create, SELECT = Read, UPDATE = Update, DELETE = Delete.

## 테이블 간의 관계

디자인 시스템에서 컬러 토큰이 버튼, 카드, 헤더 등 여러 컴포넌트에서 참조되듯, 데이터베이스에서도 테이블끼리 서로 참조한다.

예를 들어 "주문" 테이블에는 "고객 ID"가 들어가고, 이 ID는 "고객" 테이블을 가리킨다. 이렇게 하면 고객 정보를 주문마다 반복해서 적을 필요가 없다. 이것을 **정규화(normalization)**라고 하는데, 핵심은 **같은 데이터를 두 번 적지 않는다**는 원칙이다.

관계 유형은 세 가지다:
- **1:1** — 한 사람에 하나의 프로필 (여권 사진처럼)
- **1:N** — 한 고객이 여러 주문 (한 클라이언트에 여러 프로젝트)
- **N:M** — 여러 학생이 여러 수업 (여러 디자이너가 여러 프로젝트에 참여)

## ACID — 데이터가 엉키지 않는 이유

은행 송금을 생각해 보자. 내 통장에서 10만 원이 빠지고 상대에게 10만 원이 들어가야 하는데, 둘 중 하나만 되면 큰일이다. 데이터베이스는 이런 상황을 **트랜잭션**이라는 묶음으로 관리한다.

ACID는 트랜잭션이 지켜야 할 네 가지 약속이다:
- **A(원자성)**: 전부 되거나, 전부 안 되거나 (반만 적용되는 건 없다)
- **C(일관성)**: 규칙에 어긋나는 상태로 남지 않는다
- **I(격리성)**: 동시에 여러 작업이 일어나도 서로 간섭하지 않는다
- **D(지속성)**: 완료된 작업은 서버가 꺼져도 사라지지 않는다

이걸 다 외울 필요는 없다. "데이터베이스가 왜 파일보다 안전한가?"에 대한 답이 ACID라는 것만 기억하면 된다.

## 인덱스 — 목차의 힘

책에서 특정 단어를 찾을 때, 1페이지부터 끝까지 훑는 것과 뒤쪽 색인(인덱스)에서 바로 찾는 것의 차이다. 데이터베이스도 마찬가지로, 자주 검색하는 열에 인덱스를 걸어두면 조회 속도가 비약적으로 빨라진다.

다만 인덱스는 공짜가 아니다 — 데이터를 추가하거나 수정할 때마다 인덱스도 함께 갱신해야 하므로, 쓰기 속도는 느려질 수 있다. **자주 검색하는 열에만** 인덱스를 거는 게 요령이다.

## Supabase — 백엔드를 통째로 대신해주는 도구

이 수업에서 실습 도구로 사용한 것이 **Supabase**다. PostgreSQL 데이터베이스에 인증, 파일 저장소, 실시간 기능까지 묶어놓은 서비스다.

바이브 코딩에서 Supabase가 유용한 이유:
- 별도의 백엔드 코드 없이 **데이터베이스를 바로 사용**할 수 있다
- 회원가입/로그인 기능이 **내장**되어 있다
- 무료 티어로 학습에 충분하다
- AI에게 "Supabase로 게시판 만들어 줘"라고 하면 꽤 정확한 결과가 나온다

직접 서버를 세우지 않아도 되니, 비전공자가 프로토타입을 빠르게 만들기에 적합하다.

## 디자이너의 시각

디자인 업무로 비유하면:

| 디자인 시스템 | 데이터베이스 |
|-------------|-------------|
| 컬러/타이포 토큰 정의 | 테이블 스키마 정의 |
| 토큰을 컴포넌트에서 참조 | 테이블 간 관계(FK) |
| 가이드라인에 어긋나면 경고 | 제약조건 위반 시 에러 |
| 시스템 업데이트하면 전체 반영 | 정규화로 한 곳만 수정 |

데이터베이스를 처음 접하면 어렵게 느껴지지만, 결국 **"데이터를 체계적으로 정리하고, 필요할 때 빠르게 꺼내 쓰는 구조"**를 만드는 일이다. 디자인 시스템을 잘 만들어본 사람이라면 이 구조적 사고가 이미 몸에 배어 있을 것이다.
