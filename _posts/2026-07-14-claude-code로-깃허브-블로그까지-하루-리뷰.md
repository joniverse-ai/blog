18년간 브랜드를 디자인해온 사람이, 오늘은 하루 종일 터미널 앞에 앉아 있었다.
그것도 명령어를 외워서 친 게 아니라, **AI 에이전트(Claude Code)에게 말로 시키면서** 말이다.
오늘 해본 것들을 리뷰 형태로 정리해둔다.

## 오늘 한 일 한눈에 보기

1. Git이 설치돼 있는지 확인하고 사용자 정보 설정
2. GitHub 연결용 SSH 키 생성 및 연결 테스트
3. 저장소(`hello-aiffel`) 클론
4. README를 자기소개 페이지로 작성 → 커밋 & 푸시
5. 날씨·코스피/코스닥 데이터를 정리한 문서 실험 (만들고, 지우고, 되살리고)
6. `QUEST` 폴더 생성 및 과제 문서 작성
7. **Jekyll(Chirpy 테마) 기반 GitHub 블로그 구축 및 배포**

## 인상 깊었던 순간들

### 1. "설치돼 있는지부터 확인해줘"가 통한다

예전 같으면 `git --version`이 뭔지도 몰랐을 것이다.
그냥 "내 컴퓨터에 Git 있는지 보고, 없으면 깔아줘"라고 말했더니
확인하고, 이미 있으니 넘어가고, 사용자 이름과 이메일까지 설정해줬다.
**명령어를 아는 것보다 '무엇을 원하는지' 말하는 게 중요**하다는 걸 체감했다.

### 2. SSH 키 — 무섭게 생겼지만 별거 아니었다

`ed25519`니 공개키/개인키니 하는 단어들은 여전히 낯설지만,
"기존 키 있으면 절대 덮어쓰지 말고, 없으면 새로 만들어줘"라는 안전장치를 걸어두니
안심하고 맡길 수 있었다. 연결 테스트에서 `Hi joniverse-ai!` 메시지를 봤을 때
묘하게 뿌듯했다.

### 3. 지웠다가 되살리기 — 버전 관리의 감(感)

문서를 하나 만들었다가 "삭제해줘" → "다시 복구해줘"를 해봤는데,
지운 파일이 이력에 남아 그대로 되살아나는 걸 보고
'아, 이래서 개발자들이 Git을 쓰는구나' 싶었다.
디자인 작업에서 시안 버전을 파일명으로 `_최종_찐최종`으로 관리하던 나에게는
꽤 충격적인 경험이었다.

### 4. 블로그 배포에서 막혔던 지점

가장 헤맨 건 마지막, GitHub Pages 배포였다.
빌드가 계속 실패하고 404가 떴는데, 알고 보니
**저장소 설정에서 Source를 'GitHub Actions'로 바꾸는 딱 한 번의 수동 작업**이
필요했던 것. 이건 AI도 대신 못 하고 내가 직접 클릭해야 하는 부분이라,
"자동화의 경계가 어디인가"를 생각하게 됐다.

## 디자이너의 눈으로 본 소감

브랜드 디자인도 결국 **큰 목표를 작은 단계로 분해하고, 반복되는 패턴을
시스템으로 만드는 일**이다. 오늘 Claude와 한 작업도 똑같았다.
"블로그를 만들고 싶다"는 큰 요구가 → 저장소 준비 → 테마 설치 →
설정 → 배포라는 단계로 쪼개지고, 각 단계가 착착 실행됐다.

내가 하던 일과 구조가 이렇게 닮아 있다는 게 신기하면서도,
앞으로 브랜드 작업 자동화도 충분히 해볼 만하겠다는 자신이 생겼다.
