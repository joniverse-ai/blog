프론트엔드가 손님이 보는 매장이라면, 백엔드는 주방이다. 주문을 받고, 재료를 꺼내고, 요리해서 내보내는 곳. 이번 챕터에서는 그 주방이 어떻게 돌아가는지 배웠다.

---

## 서버란 무엇인가

개발할 때 자주 보는 `localhost:3000`이라는 주소가 있다. 이건 "내 컴퓨터 안에서만 돌아가는 서버"라는 뜻이다. 내 노트북이 곧 서버가 되는 셈.

실제 서비스에서는 이 서버가 내 컴퓨터가 아니라 **클라우드 어딘가에 있는 컴퓨터**에서 돌아간다. 누군가가 브라우저에 주소를 치면, 그 요청은 인터넷을 타고 그 컴퓨터까지 도달한다. 핵심은 간단하다 — 서버는 그냥 **요청을 받고 응답을 돌려주는 프로그램**이다.

## 네트워크 기초 — 편지가 도착하는 원리

웹 요청이 서버에 도달하는 과정은 편지 배달과 비슷하다.

| 개념 | 편지 비유 | 실제 역할 |
|------|----------|----------|
| **IP 주소** | 건물 주소 (서울시 강남구 ...) | 컴퓨터의 고유 번호 |
| **도메인** | 건물 이름 (○○빌딩) | 사람이 읽을 수 있는 주소 (google.com) |
| **DNS** | 건물 이름 → 주소 변환 전화번호부 | 도메인을 IP로 바꿔주는 시스템 |
| **포트** | 건물 안의 호수 (301호, 302호) | 서버 안에서 어떤 서비스로 갈지 구분 |

브라우저에 `google.com`을 치면, DNS가 이 이름을 IP 주소로 바꾸고, 그 주소의 80번(HTTP) 또는 443번(HTTPS) 포트로 요청이 간다. 디자이너가 택배 추적 번호를 몰라도 택배를 받듯, 사용자는 이 과정을 모르지만 매번 일어나고 있다.

### HTTP와 HTTPS

HTTP는 브라우저와 서버가 대화할 때 쓰는 규칙이다. 편지의 봉투 양식이라고 생각하면 된다 — "보내는 사람, 받는 사람, 내용"의 형식을 정해놓은 것.

HTTPS는 여기에 **자물쇠**를 더한 것이다. 편지를 밀봉해서 보내는 것처럼, 중간에 누가 열어봐도 내용을 알 수 없게 암호화한다. 요즘은 HTTPS가 기본이다.

## 백엔드가 하는 일 — CRUD

백엔드가 하는 일의 대부분은 네 글자로 요약된다.

| 동작 | 의미 | 카페 비유 |
|------|------|----------|
| **C**reate | 만들기 | 새 메뉴 등록 |
| **R**ead | 읽기 | 메뉴판 조회 |
| **U**pdate | 수정 | 가격 변경 |
| **D**elete | 삭제 | 단종 메뉴 내리기 |

이전 챕터에서 배운 REST API의 네 동사(POST, GET, PUT, DELETE)가 이 CRUD와 정확히 대응한다. 결국 백엔드 개발의 절반은 **"이 데이터를 만들고, 읽고, 고치고, 지우는 길을 만드는 것"**이다.

### API 엔드포인트 설계

API 엔드포인트는 주방의 서빙 창구에 붙은 번호표 같은 것이다.

```
GET    /menus         → 전체 메뉴 목록
GET    /menus/3       → 3번 메뉴 상세
POST   /menus         → 새 메뉴 등록
PUT    /menus/3       → 3번 메뉴 수정
DELETE /menus/3       → 3번 메뉴 삭제
```

규칙은 단순하다. **명사(menus)로 무엇을 다루는지** 정하고, **동사(GET/POST/...)로 어떤 행동인지** 표현한다. AI에게 "메뉴 CRUD API를 만들어 줘"라고 하면 이 구조를 자동으로 잡아준다.

## 인증 — "당신이 누구인지" 확인하기

카페에서 직원만 주방에 들어갈 수 있듯, 서버도 아무나 데이터를 건드리게 두지 않는다. 인증 방식은 크게 세 가지다.

**세션 기반**: 로그인하면 서버가 출입증(세션 ID)을 발급하고, 매 요청마다 이 출입증을 확인한다. 서버가 출입증 목록을 직접 관리해야 해서 사용자가 많아지면 부담이 커진다.

**토큰 기반(JWT)**: 출입증 자체에 "이 사람은 누구, 언제까지 유효"라는 정보를 담아서 준다. 서버는 목록을 관리할 필요 없이 출입증만 검증하면 된다.

**OAuth**: "구글로 로그인", "카카오로 로그인" 같은 것이다. 우리 서비스가 직접 비밀번호를 받지 않고, 이미 믿을 수 있는 서비스에 인증을 맡기는 방식. 사용자 입장에서도, 서비스 입장에서도 편하다.

## 배포 — 내 컴퓨터에서 세상으로

`localhost`에서만 돌아가는 서비스는 내가 노트북을 닫는 순간 꺼진다. 다른 사람이 쓸 수 있으려면 **배포**를 해야 한다.

배포는 "내 컴퓨터에서 돌아가는 코드를 인터넷에 연결된 서버에 올려놓는 것"이다. 디자인에 비유하면, Figma에서 시안을 만드는 건 개발이고, 인쇄소에 넘기는 게 배포다.

### 무료 배포 옵션들

학습 단계에서 써볼 수 있는 무료 서비스가 꽤 있다.

| 서비스 | 특징 | 적합한 용도 |
|--------|------|------------|
| **Vercel** | Next.js와 궁합이 좋음, 푸시하면 자동 배포 | 프론트엔드 + 간단한 서버 기능 |
| **Netlify** | 정적 사이트에 강점 | 포트폴리오, 랜딩페이지 |
| **Supabase** | 데이터베이스 + 인증 + 스토리지 한 번에 | 백엔드가 필요한 프로젝트 |
| **Railway** | 서버 코드를 그대로 올림 | Node.js, Python 서버 |

무료 티어에는 제한이 있지만, 학습용이나 프로토타입으로는 충분하다. 나중에 사용자가 늘면 유료로 전환하면 된다.

## 프론트와 백을 연결하기

프론트엔드와 백엔드를 따로 만들면, 결국 둘을 이어붙여야 한다. 이 과정에서 자주 마주치는 개념이 **CORS**다.

CORS는 쉽게 말해 "다른 주소에서 온 요청을 허용할 것인가?"에 대한 규칙이다. 프론트가 `localhost:3000`이고 백이 `localhost:8000`이면, 브라우저는 이걸 "다른 출처"로 본다. 서버 쪽에서 "이 주소에서 오는 요청은 괜찮아"라고 명시적으로 허용해야 한다.

처음 겪으면 당황스러운 에러지만, AI에게 "CORS 에러 해결해 줘"라고 하면 대부분 바로 잡아준다.

## 보안 — 최소한 알아야 할 것들

백엔드에서 보안이 중요한 이유는 단순하다. **데이터가 여기에 있기 때문이다.** 프론트엔드에서 아무리 버튼을 숨겨도, 백엔드로 직접 요청을 보내면 뚫린다.

기본적으로 지켜야 할 원칙:
- 사용자 입력을 **절대 그대로 믿지 않는다** (SQL 인젝션, XSS 방지)
- 비밀번호는 **암호화해서 저장**한다 (평문 저장 금지)
- API 키, DB 비밀번호 같은 민감 정보는 **환경 변수**로 관리한다
- 불필요한 정보는 응답에 포함하지 않는다

AI가 코드를 짜줄 때 보안 부분은 특히 **직접 검토**해야 한다. AI는 동작하는 코드를 잘 짜지만, 프로젝트의 보안 요구사항까지 파악하진 않기 때문이다.

## 디자이너의 시각

디자인 프로세스와 비교하면 이해가 빠르다.

| 디자인 | 백엔드 |
|--------|--------|
| Figma에서 시안 작업 | localhost에서 개발 |
| 인쇄소/웹에 게시 | 클라우드에 배포 |
| 브랜드 가이드라인 | API 명세서 |
| 시안 접근 권한 관리 | 인증/인가 시스템 |
| 클라이언트 피드백 반영 | 데이터 수정(Update) |

백엔드를 직접 코딩하지 않더라도, **무엇이 일어나고 있는지 아는 것**이 중요하다. AI에게 "회원가입 기능 만들어 줘"라고 할 때, 그 뒤에서 인증과 데이터 저장이 어떻게 흘러가는지 알면 훨씬 정확한 지시가 가능하다.
