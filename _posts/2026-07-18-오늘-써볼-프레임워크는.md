"바이브 코딩으로 웹 만들기" 첫 번째 챕터, **"오늘 써볼 프레임워크는?"**의 내용을 정리한다.
코드를 외우는 게 아니라 **왜 이런 도구가 필요한지, 어떻게 고르는지**를 배우는 챕터였다.

---

## 1. 프레임워크가 대체 뭔가요?

프레임워크는 직역하면 '뼈대'. 집을 지을 때 매번 기둥·배관을 0부터 설계하지 않듯, 웹서비스에서 반복되는 일을 미리 정리해 둔 **개발 골조**다.

- **라이브러리**: 필요할 때 꺼내 쓰는 부품 상자
- **프레임워크**: "이 안에서는 이렇게 나누고 연결하자"는 약속까지 포함

핵심 차이는 **제어의 역전(Inversion of Control)**. 라이브러리는 내가 부르지만, 프레임워크는 전체 흐름을 쥐고 내 코드를 불러준다.

## 2. 프레임워크가 풀려는 세 가지 문제

화면이 커질 때 반복해서 터지는 문제가 있다.

| 문제 | 순수 코드에서 겪는 일 | 프레임워크가 덜어주는 일 |
|------|----------------------|------------------------|
| **반복** | 비슷한 카드·버튼 코드를 여러 곳에 복사 | 한 번 만들어 여러 곳에서 재사용(컴포넌트) |
| **변화** | 상태값을 여러 코드가 따로 바꿈 | 데이터가 바뀌면 화면도 규칙대로 함께 갱신(상태 관리) |
| **연결** | 주소별로 어떤 화면을 보여줄지 헷갈림 | 폴더 구조·주소별 화면 연결을 체계화(라우팅) |

### 컴포넌트로 재사용하기

순수 JS로 카드 30개를 만들면 수정할 때 30곳을 모두 고쳐야 한다. React 같은 프레임워크에서는 카드 설계를 한 곳에 두고, 데이터만 바꿔 여러 번 불러온다. **한 곳만 고치면 30개가 모두 바뀐다.**

### 상태 관리의 힘

필터를 바꾸면 결과 목록, 결과 수, 빈 결과 안내, 페이지 제목이 모두 바뀌어야 한다. 순수 JS에서는 다섯 곳을 개발자가 하나하나 챙겨야 하지만, 프레임워크에서는 **하나의 상태를 바꾸면 나머지가 자동으로 일관되게 갱신**된다.

### CS 교양: 추상화와 모듈화

- **추상화**: 복잡한 속을 감추고 꼭 필요한 조작만 드러내기 (자동차의 페달과 핸들)
- **모듈화**: 큰 덩어리를 갈아 끼울 수 있는 조각으로 나누기 (레고 블록)

바이브 코딩에서 AI에게 지시할 때도 결국 이 두 언어로 된다. "카드를 컴포넌트로 만들어 재사용해"(모듈화), "검색 결과가 바뀌면 목록이 따라 바뀌게 해"(추상화).

## 3. 프레임워크, 몇 개나 알아야 할까

**답: 다 알 필요 없다. 대신 판단할 수 있어야 한다.**

주요 프레임워크를 범주별로 정리하면:

| 범주 | 예시 |
|------|------|
| UI 라이브러리/프레임워크 | React, Vue, Svelte, Angular, Solid, Qwik |
| 메타프레임워크 | Next.js, Nuxt, SvelteKit |
| 주변 생태계 | 라우터, 상태관리, UI 컴포넌트, 테스트 도구 |

**AI는 자료 많은 프레임워크를 더 정확히 짠다.** React 계열은 학습 데이터가 가장 많아 AI의 첫 코드가 정확하고, 규칙이 일관된 프레임워크일수록 AI가 매번 비슷한 구조로 코드를 낸다.

### 선택의 판단 축

| 판단 축 | 질문 |
|---------|------|
| AI 친화도 | AI가 정확한 코드를 잘 짜는가? |
| 러닝커브 | 팀이 받아들일 수 있는가? |
| 생태계 | 필요한 예제·도구가 충분한가? |
| 일자리·자료 | 채용 공고, 커뮤니티가 있는가? |
| 장기 유지보수 | 업데이트 정책, 보안 패치는? |

## 4. AI와 함께 PRD 만들기

좋은 개발은 "만들어 줘" 한 방이 아니라, **AI와 주고받으며 정하는 것**이다.

1. **AI에게 나를 인터뷰하게 한다** — "구체적인 PRD를 짜기 위해 정해야 할 것들을 한 번에 하나씩 물어봐 줘"
2. **프레임워크를 추천받는다** — 조건을 주고 3개 이상 장단점 비교
3. **PRD로 정리받는다** — 지금까지 대화를 문서로 남기기

프로그래밍 문법을 파고드는 것보다, **AI와 함께 만든 PRD를 꼼꼼히 읽는 것이 더 좋은 학습**이다.

## 5. 백엔드 없이 프론트엔드 만들기

백엔드 API가 아직 없어도 화면을 만들 수 있다. **목업 데이터(mock data)**를 쓰면 된다.

- 백엔드를 기다리지 않고 **병렬 개발** 가능
- 디자인과 인터랙션을 먼저 검증
- AI에게 "이 데이터로 화면 만들어줘"라고 하면 즉시 완성
- **나중에 진짜 API로 바꿀 때 한 줄만 수정**

핵심은 **관심사의 분리**: 데이터를 별도 파일로 빼두면, 백엔드가 생겼을 때 import 한 줄을 API 호출로 바꾸기만 하면 된다.

## 6. CS 교양 — API가 하는 일

API는 프론트엔드와 백엔드가 대화하는 **서빙 창구**다.

### REST API의 네 가지 동사

| 동사 | 식당 비유 | 데이터 의미 |
|------|----------|------------|
| GET | "메뉴판 보여줘" | 목록을 가져온다 |
| POST | "이거 주문할게" | 새 데이터를 만든다 |
| PUT | "주문 바꿔줘" | 기존 데이터를 수정 |
| DELETE | "주문 취소할게" | 데이터를 지운다 |

**첫 프로토타입에서는 REST + JSON이 기본.** GraphQL은 서비스가 커져서 데이터 요청이 많아질 때 고려하면 된다.

## 7. 쇼핑몰 예시로 꿰어보기

배운 것을 하나의 흐름으로 정리하면:

1. **서비스를 한 줄로 정한다** — 무엇을, 누구를 위해, 핵심 화면 3개
2. **AI에게 프레임워크를 추천받고 판단한다** — 조건을 주는 프롬프트로
3. **목업 데이터를 만든다** — 백엔드 없이 화면을 채울 가짜 데이터

예시: "수제 디저트를 파는 작은 온라인 가게, 선물용 케이크를 찾는 20~30대 대상, 상품 목록·상품 상세·장바구니 화면"

프레임워크를 고른 이유를 3문장으로 남기는 것이 **"유행 따라 골랐다"와 "조건 보고 골랐다"를 가르는 차이**다.
