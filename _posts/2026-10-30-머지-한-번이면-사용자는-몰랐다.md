이번 모듈 이름이 "프로덕트 설계부터 서비스 배포 전략까지"였어. 2주 동안 AI 친구 에이전트 하나를 붙잡고, 내 노트북에서 돌던 걸 **진짜 서비스**로 내보냈거든. 돌아보니까 매일 던진 질문이 조금씩 바뀌더라.

![2주 지도]({{ "/assets/img/2026-10-30/module-map.svg" | relative_url }})

결론부터 말할게. 마지막 날엔 PR 하나 머지하고 승인 버튼 누르는 동안 production에 요청을 **1,467번** 보냈는데, 실패는 **0번**이었어. 거기까지 어떻게 갔는지 같이 따라가 보자.

---

## 1주차 · 만들고 내보내기

**1장 설계.** 첫날은 코드를 한 줄도 안 짰어. "이 기능을 사람들이 어디서 쓰지?"부터 정했거든. 채널은 기능이 아니라 **사용 맥락**이 정하고, 코드 전에 사람이 AI인 척하는 "오즈의 마법사 테스트"로 먼저 검증해. 디자이너한텐 익숙한 순서라서 반가웠어. 시안 전에 리서치부터 하는 거랑 똑같잖아.

**2장 첫 배포.** Cloud Run에 처음 올렸는데 바로 실패했어. 화면엔 "8080 포트에서 기다리지 않았다"라고 떴는데, 진짜 원인은 **그 위 로그**에 있었어. "API 키가 없어서 앱을 시작하지 않습니다." 키는 `.env`에만 있었고, `.env`는 업로드되지 않거든. 그래서 키를 **Secret Manager(금고)**에 넣고 서비스에는 이름만 연결했어.

**3장 운영.** 이제 "올라갔나?"가 아니라 "계속 잘 돌아가나?"를 물어. AI 답은 느리니까 타임아웃을 넉넉히 잡고, 돈은 대부분 Cloud Run이 아니라 **LLM 호출**에서 나간다는 것도 알게 됐어. 그리고 여기서 처음 경고를 들었어. 대화를 서버 메모리에 두면 **배포할 때마다 사라진다**고. (이 얘기는 2주차에 다시 나와.)

**4장 자동 배포.** main에 머지하면 GitHub Actions가 알아서 배포해. 키 파일 대신 **Workload Identity Federation**으로 "내 저장소에서 온 요청일 때만" 배포 권한을 빌려주는 게 핵심이었어. 근데 함정이 있었어. **켜지기는 하는데 틀린 코드**는 그대로 사용자한테 나가더라. 약속 시각이 9시간 늦게 저장되는 버그가 실제로 하루 동안 서비스됐어.

**5장 CI · staging.** 그래서 문을 세웠어.

![코드가 사용자에게 가는 길에 세운 문들]({{ "/assets/img/2026-10-30/gates.svg" | relative_url }})

일부러 망가뜨린 PR 네 개로 시험해 봤는데, 어디서 걸렸는지 보면 각 문이 왜 필요한지 바로 보여.

| 망가진 PR | 바뀐 것 | 어디서 걸렸나 |
|---|---|---|
| A | 위기 표현 판정을 "똑같을 때만"으로 | CI |
| B | 날씨 키워드를 좁힘 | CI |
| C | 약속 시각에서 시간대를 뺌 | CI (서버와 같은 UTC 러너에서만!) |
| D | 보내기 버튼 CSS `display:none` 한 단어 | **staging에서 내 눈으로** |

D가 제일 기억에 남아. 테스트는 화면을 안 보니까 통과했고, staging에서 직접 써 보다가 "어? 버튼이 없네" 했거든. 디자이너 눈이 마지막 문이었던 셈이야.

## 2주차 · 끊김 없이 내보내기

**6장 Dockerfile.** 사진에서 글자를 읽는 OCR을 붙이니까, 코드만 올리는 방식으로는 운영체제 프로그램(`tesseract`)을 못 챙기더라. 그래서 "이 환경에서 이렇게 실행해"를 Dockerfile에 직접 적었어. 어디서 만들어도 같은 결과가 나와. 브랜드 키트 같은 거지.

**7장 이미지는 한 번만.** "지금 production이랑 staging에서 확인한 거, 같은 거야?"에 답을 못 했어. 둘이 **따로 빌드**하고 있었거든. 이제 이미지는 Actions에서 한 번만 만들고, staging에서 본 **바로 그 이미지**를 production에 올려(승격).

**8장 로드밸런서.** Cloud Run이 해 주는 걸 이해하려고 내 Mac에 Nginx로 직접 만들어 봤어. 전환은 실패 0건이었는데, 넘기자마자 방금 만든 약속이 **0개**가 됐어. 3장의 경고가 눈앞에서 일어난 거야. 그래서 대화를 Supabase(데이터베이스)로 옮겼어.

> **"요청이 안 끊김"이랑 "하던 일이 이어짐"은 따로 봐야 한다.**

**9장 Cloud Run 무중단.** 여기서 "배포 성공"을 믿으면 안 되는 이유를 숫자로 봤어.

![프로브별 실패 수]({{ "/assets/img/2026-10-30/probe-chart.svg" | relative_url }})

Cloud Run은 기본적으로 포트만 열리면 "준비 끝!" 하고 손님을 넘겨. 그래서 배포 명령은 "Done"인데 사용자는 503을 34번 받았어. 검사를 `/health`로 바꾸니 0건이 됐지. 그다음 손으로 블루그린과 카나리를 해 보고, 그 절차를 워크플로로 옮겼어.

![내 배포 흐름]({{ "/assets/img/2026-10-30/deploy-flow.svg" | relative_url }})

빈칸은 내가 직접 정했어. 다 손으로 한 번씩 해 보고 정한 거라 이유가 있어.

- **스모크 테스트는 꼭 태그 URL로.** 서비스 주소로 물으면 아직 0%인 새 버전 대신 이전 버전이 대답해. 그럼 망가진 버전도 통과해 버려.
- **전환은 `--to-latest`로.** 리비전을 콕 집어 옮기면 트래픽이 거기 고정돼서, 다음 배포의 새 버전이 0%에 남아. 실제로 겪었어 😱
- **카나리 대신 블루그린.** 10%로 정했더니 실제론 13%였고, 1분에 150번을 보내도 10% 쪽은 19건뿐이었어. 사용자가 적으면 숫자가 안 쌓여.

![production 배포와 롤백 기록]({{ "/assets/img/2026-10-30/proof-bar.svg" | relative_url }})

마지막으로 일부러 망가진 버전도 올렸어. 1주차에 세운 CI가 먼저 막아서 머지조차 안 되더라 ㅋㅋ 그래서 서버에서만 깨지는 버전으로 바꿨더니, 이번엔 Cloud Run 검사에서 걸렸어.

![안전장치 세 겹]({{ "/assets/img/2026-10-30/safety-layers.svg" | relative_url }})

## 디자이너의 눈으로 다시 보면

2주 동안의 키워드를 브랜드 리뉴얼로 바꿔 보면 이래. 나한텐 이게 제일 오래 남을 것 같아.

| 배포 용어 | 브랜드 리뉴얼로 치면 |
|---|---|
| 설계 · 오즈의 마법사 테스트 | 시안 전에 하는 **리서치와 목업 테스트** |
| Secret Manager | 원본 파일은 **금고**에, 협력사엔 열람 권한만 |
| CI 테스트 | 인쇄 넘기기 전 **자동 교정** (오탈자, 규격) |
| staging | **가제본** 받아서 직접 넘겨 보기 |
| production 승인 | 최종 **컨펌** 도장 |
| Dockerfile | 어느 지점에서든 똑같이 나오는 **브랜드 키트** |
| 이미지 승격 | 감리 본 **그 인쇄판**으로 찍기, 다시 출력하지 않기 |
| 블루그린 + 0% 배포 | **가림막 뒤에서** 새 간판 달고, 나만 들어가 보고, 오픈 때 걷기 |
| 롤백 | 옛 간판을 **창고에** 둬서 몇 초 만에 다시 걸기 |

## 아직 못 재는 것

- 지금 검사는 서버가 살아 있는지, 커밋이 맞는지만 봐. **친구의 답이 이상해졌는지는 몰라.**
- 버튼이 사라지는 같은 화면 문제는 아직 사람 눈(staging)에 기대고 있어.
- staging이랑 production이 같은 실행 계정을 써서, 권한을 아직 못 나눴어.

첫날 나는 "AI 기능 하나 만드는 건 하루면 되는데, 사람들이 계속 쓰게 하는 건 왜 오래 걸리지?"라는 질문으로 시작했거든. 이제 조금 알 것 같아. 만드는 것과 **내보내는 것**은 다른 일이고, 내보내는 일은 결국 **언제 준비됐다고 볼지, 트래픽을 어디로 보낼지, 그동안 요청을 실제로 셌는지**를 내가 정하고 숫자로 증명하는 거였어. 초록 체크 ✅ 너머를 볼 수 있게 된 2주였어.
