어제는 트레이스를 열어서 하루가 **어디서 엉뚱한 답을 했는지** 찾았잖아. 오늘은 그다음 질문이었어.

> "그래서 고쳤다는 건 어떻게 알아?"

지시문에 규칙 한 줄 넣고, 대화 한 번 다시 보내 보고, 이번엔 맞게 답하면… "괜찮아 보인다"로 내보냈겠지. 오늘은 그걸 하지 않는 법을 배웠어. **무엇이 실패인지, 무엇으로 판정했는지, 무엇과 비교해 나아졌는지**를 말할 수 있어야 고쳤다고 말하는 거래.

---

## 먼저 실패를 읽는다

지표부터 고르지 않아. 별로예요가 붙은 트레이스랑 아무거나 고른 트레이스를 **직접** 읽고, 단계별 입력과 출력을 보면서 **처음 어긋난 단계**로 묶어.

해 보니 같은 '공휴일' 실패인데 고칠 곳이 다 달랐어.

![처음 어긋난 단계로 묶은 실패]({{ "/assets/img/2026-11-03/failure-steps.svg" | relative_url }})

그리고 유형마다 **판정 기준 문장**을 썼어. 다른 사람이 읽어도 같은 답에 같은 판정을 내릴 수 있게.

- ❌ "정확하게 답한다"
- ✅ "답에 나온 공휴일 날짜는 모두 도구 결과에 있다"

디자인 리뷰에서 "좀 더 세련되게"가 아니라 "제목과 본문 대비가 4.5:1 이상"이라고 말해야 다음 사람이 같은 걸 고칠 수 있는 거랑 똑같더라.

---

## 데이터셋과 LLM 심사, 그런데 심사도 틀린다

실패를 **데이터셋**(고정한 입력 + 기대 결과)으로 만들었어. 포인트는 하나야. 답이 앞 단계 결과에 따라 흔들리면 **앞 단계 결과를 고정해서** 넣는 것. 그래서 공휴일 답 데이터셋은 이렇게 생겼어.

| 메시지 | 고정한 도구 결과 | 통과 조건 |
|---|---|---|
| 12월에 연휴 있어? | 12월 25일(금) 크리스마스. | 25일(금)~27일(일) 주말과 이어 사흘 쉰다고 말한다 |
| 이번 달에 공휴일 있어? | 11월에는 공휴일이 없습니다. | 결과에 없는 날짜를 공휴일이라고 말하지 않는다 |

실패 6개, 정상 6개, 총 12개. 정답이 하나인 건(도구 이름, 날짜) **코드**로 채점하고, 읽어야 아는 건(연휴를 말했나, 지어냈나) **LLM 심사**(LLM-as-a-Judge)한테 맡겼어. 심사 모델은 답 모델(gpt-4o-mini)보다 한 단계 큰 gpt-4o로.

그리고 첫 실험 결과… **12개 다 통과.** 기분 좋을 뻔했는데, 답을 직접 읽어 보니 "다음 공휴일은 내년 1월 1일"처럼 **결과에 없는 날짜를 말한 답까지 통과**시켰더라. 설정을 열어 보니 심사 지시문 칸에 템플릿 기본 문장이 그대로 저장돼 있었고, 평가 규칙도 두 개가 겹쳐서 항목마다 점수가 두 개씩, 그것도 서로 다르게 붙어 있었어 😅

![심사와 사람 판정의 일치율]({{ "/assets/img/2026-11-03/judge-agreement.svg" | relative_url }})

그래서 오늘 제일 오래 한 일은 사실 **심사를 사람 판정과 맞추는 일**이었어. 고치고 재 보고, 또 고치고 재 보고. 마지막엔 모두 통과가 나오길래 "이번엔 너무 후해진 거 아냐?" 싶어서, 오늘 실제로 나왔던 **틀린 답 6개**를 일부러 넣어 봤어. 6개 다 실패로 잡더라. 그제야 믿고 쓰기로 했어.

---

## 지시문 한 줄 vs 도구 코드

이제 진짜 고칠 차례. 연휴 항목 4개가 매번 실패했거든. 금요일 크리스마스를 두고 "연휴는 없네"라고 하는 거야.

처음엔 당연히 지시문에 한 줄 넣었지. *"공휴일이 금요일이나 월요일이면 주말과 이어 사흘 쉰다고 말한다."* 점수가 올랐어. 7.5개 → 9개. 근데 항목별로 읽어 보니까…

> "이번 주에 쉬는 날 있어?" → "응, 이번 주 **금요일이 공휴일**이라서 주말과 이어서 사흘 쉬는 거야!"

도구 결과는 분명히 "이번 주 공휴일 없음"이었어. 새 규칙의 "금요일이면 사흘"이라는 말에 끌려서 **없는 연휴를 지어낸 거야.** "사흘(24일~26일)"처럼 날짜를 틀리게 세기도 했고.

그래서 방향을 바꿨어. **지시문은 한 글자도 안 건드리고**, 공휴일 도구가 결과에 처음부터 이렇게 넣게 했어.

```
12월 25일(금) 크리스마스. 주말과 이어 쉬는 연휴: 12월 25일(금)~27일(일) 사흘.
11월에는 공휴일이 없습니다. 그 뒤 첫 공휴일: 12월 25일(금) 크리스마스.
```

![지시문 한 줄 vs 도구 코드]({{ "/assets/img/2026-11-03/reply-scores.svg" | relative_url }})

**12개 다 맞았어.** 두 번 돌려서 두 번 다. 지어낸 날짜는 0개. 모델은 계산된 걸 읽어서 전하기만 하면 되니까.

오늘의 한 줄은 이거였어. **해석은 프롬프트로, 계산과 사실은 코드로.** 지시문은 모델이 연휴를 "말하게"는 할 수 있어도, "맞게 세게"는 못 하더라.

덤으로 배운 것도 있어. 도구를 바꾸자마자 심사 점수가 75%로 떨어졌거든(위 그래프 가운데). 심사 지시문 예시에 *"11월 없음 → '다음은 12월 25일' → 실패 (결과에 없는 날짜)"*가 있었는데, 이제 도구가 12월 25일을 결과에 넣어 주니까 이 예시가 **정답을 실패라고 가르치는 예시**가 돼 버린 거야. 데이터셋, 도구, 심사는 한 묶음이라 하나를 고치면 셋 다 다시 맞춰 봐야 해.

## 도구 고르기 지시문도 버전으로

도구를 고르는 지시문(router)은 코드 밖 Langfuse **프롬프트 관리**로 옮겼어.

- 저장할 때마다 **버전**이 쌓이고, 한 번 만든 버전은 못 고쳐.
- 서비스는 버전 번호 대신 **라벨**로 가져와. 운영은 `production`, 테스트는 `staging`.
- **배포 = 라벨 옮기기, 롤백 = 옛 버전에 라벨 다시 붙이기.** 코드 배포 없이 몇 초.
- Langfuse에 못 닿으면 코드에 남긴 원래 문장으로 답하게 했어. 일부러 없는 라벨을 불러 봤는데 멀쩡히 답하더라.

교안에 나온 규칙 두 줄(공휴일 기간, 시험 전날 계산)을 더한 v2를 만들어서 41개 전체로 두 번씩 돌렸어.

![router v1과 v2 비교]({{ "/assets/img/2026-11-03/router-compare.svg" | relative_url }})

- **다음 공휴일(T26)**: 고쳐졌어. "기간을 말 안 하면 인자를 비운다"는 **해석**의 문제라서.
- **시험 전날(T34)**: 네 번 다 **같은 틀린 날짜**. 흔들림이 아니라 모델이 **계산**을 못 하는 거야 → 코드로 옮길 일.
- **내일 날씨(T13)**: 원래 잘 되던 건데 v2에서 두 번 다 미세먼지 도구를 덧붙였어. **회귀**야. 고친 항목만 봤으면 못 봤겠지.

총점만 봤으면 "v2가 1점 낮네" 하고 끝났을 거야. 항목별로 봐야 이유가 보여. 그래서 production은 v1 그대로 뒀어.

## A/B 테스트는 언제 쓰나

데이터셋 실험으로는 "사용자가 짧은 답을 더 좋아하나" 같은 건 못 가려. 그건 실제 사용자 반응을 봐야 해. 그래서 A/B 테스트도 넣어 봤어.

- 메시지마다 무작위가 아니라 **사용자 ID 해시**로 그룹을 정해. 한 사람이 메시지마다 다른 성격을 만나면 안 되니까.
- 시크릿 창이랑 다른 주소로 사용자를 여러 명 만들어 보니, 같은 사람은 늘 같은 그룹이었고 a, b 둘 다 기록됐어.

근데 계산해 보면 현실이 보여. 하루 메시지가 50건이면 별로예요 20%→15% 차이를 가리는 데 **1년 가까이** 걸린대. 그래서 우리 같은 작은 서비스에서는 **데이터셋 실험이 판단의 중심**이고, A/B는 "새 버전이 크게 나빠지진 않았나" 지켜보는 용도로만 쓰기로.

## 마지막으로, 빠뜨릴 수 없게

이 모든 확인을 다음에 누가 급하게 고칠 때 다시 하리라는 보장은 없잖아. 그래서 **평가 관문**을 GitHub Actions에 걸었어.

- PR에 `eval` 라벨을 붙이면 실제 LLM으로 도구 선택 41개를 채점해.
- 기준(도구 35개, 인자 32개)에 못 미치면 빨간 ✗, 머지를 막아.
- PR마다 자동으로 돌리면 돈이 쌓이니까 **라벨이나 버튼으로만** 돌게 했어.

오늘 PR에 라벨을 붙였더니 38/41, 34/41로 초록불. 기준은 일부러 지금 결과보다 조금 낮게 잡았어. 같은 코드로도 실행마다 한두 개씩 흔들리거든.

## 디자이너의 눈으로 다시 보면

| 오늘 배운 것 | 디자인으로 치면 |
|---|---|
| 판정 기준 문장 | "세련되게" 말고 "대비 4.5:1 이상" 같은 **검수 기준** |
| 데이터셋 | 시안을 매번 같은 **테스트 화면 세트**에 얹어 보기 |
| LLM 심사 | 검수를 대신해 주는 동료. 처음엔 **내 판정과 맞는지** 같이 봐야 함 |
| 회귀 확인 | 버튼 하나 고쳤더니 다른 페이지가 깨졌나 **전체 페이지 훑기** |
| 프롬프트 라벨 | 확정안에 붙이는 **FINAL 스티커**. 옮기면 배포, 되돌리면 롤백 |
| 평가 관문 | 인쇄소 넘기기 전 **필수 교정 단계** |

결국 오늘 배운 건 **"감"을 "검수 기준"으로 바꾸는 법**이었던 것 같아. 아침엔 "괜찮아 보인다"였다면, 이제는 "기준 문장 이거, 심사 판정 이거, v1이랑 비교해서 이만큼"이라고 말할 수 있어.

## 다음에 고칠 것

- 시험 전날 계산을 코드로 옮기기. 기존 날짜 코드도 "전날"을 몰라서 금요일 당일로 계산하더라.
- 도구 고르기 단계의 트레이스에 실제로 넣은 [지금]과 [달력]도 남기기. 지금은 메시지만 남아서 나중에 다시 만들기 어려워.
- 평가 관문 기준을 실제 CI에서 몇 번 더 돌려 보고 다시 정하기.
